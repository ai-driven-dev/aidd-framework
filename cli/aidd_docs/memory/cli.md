# CLI

The `aidd` command-line tool: its commands, inputs, and distribution.

## Commands

Thirty-three leaf commands. Read them live — `aidd --help`, then each group's. `scripts/smoke-tools.sh` exercises every one and fails when its list drifts from the binary's.

- `setup`, `doctor`, `sync`, `clean` — bring a project to a correct state, then keep it there
- `framework install | update | remove | rules` — the framework's lifecycle on a tool, chosen by `--tool <id>`
- `plugin install | list | remove | search | update`
- `marketplace add | list | remove | refresh | check`
- `auth login | logout | status`
- `telemetry on | off | read | report | check | forget | identity` — `identity` carries `use | off | link | unlink`
- `translate <source>` — author-side, converts a source into a target-native plugin tree
- `update` — the CLI itself, aliased `upgrade`

## Interface

- Parser: `commander` (`src/cli.ts`). A `preAction` hook builds the dependency graph once per project root.
- No argument on a TTY runs the interactive menu and never reaches the parser. No argument without one prints help.
- Global flags: `--version`, `--verbose`. Interactive by default; a non-TTY needs explicit flags or exits 1.
- Text on stdout, errors on stderr (`src/presentation/output.ts`). Typed exceptions travel inward, caught at the command layer only (`src/presentation/error-handler.ts`).
- The update-check hook is the one place that swallows: it must never fail the command a person asked for.
- Exit codes: `0` ok; `1` on error, an unhealthy `doctor`, or a non-interactive guard.
- `doctor`, for a tool whose plugins activate through its own CLI (claude, codex, copilot): compares `nativeRegistrations` against that host's own registry file, four answers — `registered` (no issue), `not-registered` and `registered-disabled` (`error`, gate `doctor` unhealthy, fix names `aidd sync` or `aidd framework install --tool <id>`), `unanswerable` (`info`, never gates — the normal state on a machine that has never run the tool's own binary). A fifth, separate pass, `checkMarketplaceSources`, is not one of those four answers: it reads a host's own marketplace registry (claude today), by the catalog's own declared name — `hostName`, never this project's own local `alias`, which is free to differ — and reports, `error`-severity, a name already registered under a *different catalog* (a different declared name or plugin set — read from each side's own `marketplace.json`, never the version and never from paths). The same catalog registered from a different, merely resolved-differently path is not a conflict — two independent projects on one machine both auto-registering the framework's own name measure exactly that — and a registered source whose catalog can no longer be read is a dead entry a re-add repairs, not a conflict either.
- `sync` restores tracked files, then drives native activation the same way `setup` and `framework install` do (`MarketplaceSyncSettingsUseCase.execute`, restoration first, activation after — reversing the order would hash a settings file restoration is about to overwrite). A manifest that exists but whose registry names no marketplace at all — a fresh clone, whose committed `.aidd/manifest.json` predates this machine's own `userConfigDir()/marketplaces.json` — is no longer a silent no-op: `sync` re-registers the framework marketplace itself, the same default `setup`'s own auto-register uses, then proceeds. Whenever the framework marketplace resolves to scope `"user"`, `sync` (like `setup`) also records this project's own claim on the shared source in `userConfigDir()/references.json` — see `architecture.md`. `sync --tool <id>` narrows activation to that tool alone. A tool whose binary is absent warns that its plugin will not load until that CLI has run and still exits `0`; a genuine activation failure (not the recoverable, best-effort kind) throws `SyncFailedError` and exits `1`. Before ever calling a host's own `marketplace add`, `registerMarketplace` checks that host's registry (claude today) itself for the same catalog-identity fact `checkMarketplaceSources` reads, and refuses there rather than silently repointed the way the host's own CLI would — counted among `SyncFailedError`'s errors, read and printed the same way by `sync`, `plugin install | remove | update`, and `marketplace add | remove | refresh` alike, so all seven commands now exit non-zero on a marketplace-name conflict that used to pass silently (or, for the `marketplace` group, print a false `registered.`/`removed.` success). `sync` also migrates a project installed *before* the shared source existed: a project-scope `aidd-framework` registry entry is retired to the machine-scope one on every run, not only when the registry is empty, carrying forward the entry's own recorded source (never `MarketplaceRegisterFrameworkUseCase`'s own local-path default) — the same thing whether it is *this* project's own entry or the host still tracking *another*, not-yet-migrated project's per-project cache, in which case `sync` repoints the host without breaking that other project and records both projects' own claim in `references.json`. Claude's own `add` overwrites silently, no prior `remove`; codex and copilot, which have no readable marketplace registry this CLI can check first, reclaim the reserved framework name specifically — `remove` then `add` — on any refusal at that name and scope, never for an arbitrary marketplace, since every registration under it is this CLI's own catalog and never a different project's. This project's own stale `.aidd/cache/built/aidd-framework/` is deleted only once the run reports no error, no tool's own binary was missing and no tool's build failed — a host's own CLI needs that tree to still resolve what it is unregistering, and a binary that never ran, or a build that never completed, cannot yet have resolved against it. `doctor` warns naming `aidd sync` for this same state whether the registry itself still records project scope or only the host lags behind an already-migrated entry.
- `clean` leaves nothing of aidd's, in the project or on the machine, and never removes anything aidd did not write — with one deliberate exception: the `aidd-framework` marketplace is machine-scope (`architecture.md`), shared by every project, so `undoMarketplaceRegistration` refuses to call a host's own `removeMarketplace` for it and warns that it is left registered instead, naming the three things that survive: the host's own registration, the `userConfigDir()/marketplaces.json` entry, and this tool's own plugin cache (its absolute path, when the tool's profile declares one); this project's own plugin refs are still uninstalled from that host regardless. Before that, `clean` drops this project's own claim on the shared source from `userConfigDir()/references.json` — once, regardless of how many tools' own registrations name it — and the warning names how many other projects still reference it, or, once none do, that `clean --scope user` is what purges the source (this project-scope run never does). A dry-run reads and reports the same count without dropping anything. `aidd marketplace remove aidd-framework` refuses the host-side unregister the same way, for the same reason — nothing removes this entry from that command; it is removed with the framework itself, by `aidd clean --scope user`. `doctor` separately warns, never errors, when a host's registered source already follows a *newer* aidd version than this run's own (naming `aidd update` — refusing to write backward is what `sync`'s own write path now does too, not just what `doctor` observes after the fact) or still the pre-migration per-project cache (naming `aidd sync`) — both decided from the registered path's own version segment, never a catalog read. Order is a hard constraint: (1) undo a host's own native registration through that host's own CLI — `uninstallPlugin` for every recorded ref, then `removeMarketplace` at the scope it was added at, because only Copilot declares a force-remove argument and Claude/Codex can refuse to drop a marketplace that still has plugins on it — before (2) tracked files, merge files and plugin files are deleted, before (3) `.aidd/` itself, since a host's own CLI needs the built tree under `.aidd/cache/` to still exist to resolve what it is unregistering. A tool whose binary is off `PATH` gets named and left alone, never touched by `rm`. (4) Machine-local files no `plugins[].files` entry tracks — `.claude/settings.local.json`, and a project-scope-merged `.cursor/hooks.json` plus its plugin's own `.cursor/hooks/<plugin>/` — are removed through the same unmerge `plugin remove` already drives for one plugin (`application/shared/remove-project-hooks.ts`). (5) A user-scope plugin's own directory (`~/.cursor/plugins/local/<plugin>`) is deleted only once its real, `realpath`-resolved location is proven to sit strictly inside the tool's declared user-scope directory (`domain/plugins/user-scope-containment.ts`) — a `..` segment a corrupted manifest entry carries, or a plugin directory that became a symlink after install, is left in place and named rather than followed. (6) Right after step (1), for every tool `undoNativeRegistrations` actually drove: the cache root its profile declares (`NativeActivation.pluginCacheDir`) is purged one marketplace at a time, `<root>/<hostName>` checked through the same containment as (5) — never on the manifest's word alone, since that name is global to the machine, not to this project. A profile declaring `marketplaceRegistry` alongside it (claude) gets the full purge, gated on a fresh read of that registry no longer naming the host — measured: claude marks an orphaned tree `.orphaned_at` but never deletes it. A profile declaring `pluginCacheDir` alone, no `marketplaceRegistry` (codex), is purged only once proven empty instead — measured: codex's own `plugin remove` deletes the content but leaves the now-empty shell, which is exactly the residue `smoke:real` left in the real `$HOME` before this existed. A tool declaring neither (copilot) is never touched.
- `clean --scope user` is the machine-scope counterpart, and the one command that does purge the shared source: `marketplace remove` still exposes no `--scope user` flag and still refuses, for the same reason as above. A `--scope user` manifest is optional: a plain project-scope `setup` never writes one, yet still leaves every whitelist entry below behind. When none exists, steps (1)-(3) below have no recorded registration to undo and are skipped outright — the result and the printed output both say plainly that no host registration was undone because nothing was registered at user scope, and, when `references.json` still lists other projects, they are named too, with the instruction to run `aidd clean` in each of them before `aidd clean --scope user`, since those projects' own hosts still resolve the shared source. Step (4), the whitelist purge, always runs regardless — it is a fixed set of paths under `userConfigDir()`, none of it read from the manifest. Order otherwise: (1) uninstall every recorded plugin ref and (2) unregister every marketplace, both through each tool's own CLI at scope `"user"` always, never omitted or guessed from the host's own default; (3) only then is each tool's own declared cache purged, the same `purgeAllNativeCaches` pass `clean` (project scope) already drives, shared rather than copied so a symlink-escape or an unconfirmed removal is caught once; a binary off `PATH` is named, with what it would have undone, and its cache is left alone. (4) A strict, hardcoded whitelist under `userConfigDir()` is then removed — `cache/built/` in full (every version, not only this run's own, plus its own now-empty `cache/` shell) and `references.json`, both re-resolved through `realpath` and `isStrictlyWithinUserScope` immediately before deletion; `manifest.json` (through its own repository, never a second path to the same file) and the `aidd-framework` entry alone out of `marketplaces.json` (through the marketplace registry) need no such resolution, since neither ever takes a path from what the manifest says — each computes its own path from `userConfigDir()` directly. `userConfigDir()` itself is never an eligible candidate either way; a user-scope plugin's own tree (Cursor) the manifest lists is removed under the same containment `clean` already trusts. Confirmation, unless `--force`, names the source, every version found under `cache/built/`, and every project `references.json` still lists as referencing it (a project whose own path no longer exists is left out), carrying the same no-registration note when there is one — `--force` proceeds regardless; a project still pointed at the now-purged source repairs itself on its own next `aidd sync`, which re-registers the shared source.

## Distribution

- npm bin `aidd` → `dist/cli.js`. Single ESM bundle; the five JSON schemas beside it are read from disk at runtime, so `files` must keep shipping them.
- Run through `npx @ai-driven-dev/cli@latest`, or install globally. Build and publish: `deployment.md`.
- `AIDD_USER_CONFIG_DIR` relocates `userConfigDir()` outright, which today moves five things at once, not only `auth.json`: the shared `aidd-framework` marketplace registration (`marketplaces.json` plus its `cache/built/<version>/`), the machine's own project-reference registry (`references.json`), and the `--scope user` manifest (`manifest.json`) — see `architecture.md`. Never the variable a team shares (`telemetry.md`).
